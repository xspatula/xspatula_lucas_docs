Reference page — not required reading to complete the [Load LUCAS 2009][load_lucas_2009]
walkthrough, only if you want the detail behind its observation-log and observation steps —
laboratory, spectral, landscape (land cover/use) and biogeographic region (BIOGEO16).

## Two kinds of observation

LUCAS 2009 records two different shapes of measurement, and the underlying `manage_observation`
process stores them in different tables depending on the shape of the `@`-prefixed parameter
value it's given:

| Measurement shape | Example | Stored in |
|---|---|---|
| Single value per indicator (laboratory) | `@ph-h2o: 6.8` | `observation.observation_measurement` |
| Array per indicator (spectra) | `@diffuse reflectance: [0.34, 0.34, ...]` | `observation.observation_measurement_array` |

Both kinds share the same `observation.observation` record shape otherwise — an observation log,
sample, provision, subsample, replicate, and timestamp — the only difference is which child table
the indicator's value lands in.

## Laboratory observations

LUCAS 2009 ships pre-measured lab soil properties directly in the source CSV — there's no
separate wetlab workflow or instrument to register, just one observation log and one observation
record per sample, both generated by `lucas_2009_to_xspatula.py`.

### Laboratory observation log

Links the campaign's sampling log to the `lucas wetlab 2009` provision — the lab analysis
"instrument," in Xspatula's terms, even though it's really a set of standard lab methods rather
than a single physical device.

**Notebook cell**: 3.4.1 Load LUCAS 2009 laboratory observation log (2015: 4.4.1) in `insert_lucas_data.ipynb`

**Job file**: `xspatula_lucas/lucas/import_data/LUCAS_2009/job_LUCAS_2009_observation_log_lab.json`

```json
{
  "process": {
    "job_folder": "import_data/LUCAS_2009/process_lab/observation_log",
    "process_sub_folder": "manage_process",
    "pilot_file": "xspatula_add_observation_log_pilot.txt"
  }
}
```

**Generated by**: `step2_observation_log()`, written to
`process_lab/observation_log/manage_process/lucas european union 2009@lucas wetlab 2009_observation_log.json`:

```json
{
  "process": [
    {
      "process": "manage_observation_log",
      "parameters": {
        "sampling_log_id__sampling_log_name": "lucas_eu_2009",
        "provision_id__provision_name": "lucas wetlab 2009",
        "contact_name": "inherit",
        "contact_email": "inherit",
        "preparation_id__preparation_name": "ds2",
        "preservation_id__preservation_name": "ds2",
        "storage_id__storage_name": "amb",
        "laboratory": 1
      }
    }
  ]
}
```

There is no `name`: the framework composes it as `lucas european union 2009@lucas wetlab 2009` (tag
`lucas_eu_2009@lucas-lab-2009`) from the sampling log and the provision — see
[Auto naming and tags explained][auto_naming_explained].

### Laboratory observations

One record per CSV row that has at least one measured indicator. Each `@`-prefixed indicator
value below is a single number, stored in `observation.observation_measurement`.

**Notebook cell**: 3.4.2 Load LUCAS 2009 laboratory observations (2015: 4.4.2) in `insert_lucas_data.ipynb`

**Job file**: `xspatula_lucas/lucas/import_data/LUCAS_2009/job_LUCAS_2009_observation_lab.json`

```json
{
  "process": {
    "job_folder": "import_data/LUCAS_2009/process_lab/observation",
    "process_sub_folder": "manage_process",
    "pilot_file": "xspatula_add_observation_pilot.txt"
  }
}
```

**Generated by**: `step6_lab_observation()`, one process file per sample under
`process_lab/observation/manage_process/`:

```json
{
  "process": [
    {
      "process": "manage_observation",
      "parameters": {
        "observation_log_id__observation_log_name": "lucas european union 2009@lucas wetlab 2009",
        "sample_id__sample_name": "<POINT_ID>@0-20",
        "provision_id__provision_name": "lucas wetlab 2009",
        "subsample": "a",
        "replicate": 0,
        "observed_at": "<date, ISO 8601>",
        "@cf": "<coarse fragment %>",
        "@clay": "<clay %>",
        "@silt": "<silt %>",
        "@sand": "<sand %>",
        "@ph-cacl2": "<pH in CaCl2>",
        "@ph-h2o": "<pH in H2O>",
        "@c-org": "<organic carbon>",
        "@caco3": "<CaCO3>",
        "@n-tot": "<total nitrogen>",
        "@p-ext": "<extractable phosphorus>",
        "@k-ext": "<extractable potassium>",
        "@cec": "<cation exchange capacity>"
      }
    }
  ]
}
```

Missing, invalid (negative, or zero where zero is not a real result) or excluded values are
omitted from that row's parameters, and values below the detection limit (e.g. `<6`) are written
as half the limit — see [Data cleaning][data_cleaning]. The `@`-prefixed indicator keys are thus
optional, not fixed-width.

| CSV column | Parameter | Indicator | Unit |
|---|---|---|---|
| `coarse` | `@cf` | Coarse fragments | weight percent |
| `clay` | `@clay` | Clay content | weight percent |
| `silt` | `@silt` | Silt content | weight percent |
| `sand` | `@sand` | Sand content | weight percent |
| `pH.in.CaCl2` | `@ph-cacl2` | pH in CaCl₂ | pH |
| `pH.in.H2O` | `@ph-h2o` | pH in H₂O | pH |
| `OC` | `@c-org` | Organic carbon | g/kg |
| `CaCO3` | `@caco3` | Calcium carbonate | g/kg |
| `N` | `@n-tot` | Total nitrogen | g/kg |
| `P` | `@p-ext` | Extractable phosphorus | mg/kg |
| `K` | `@k-ext` | Extractable potassium | mg/kg |
| `CEC` | `@cec` | Cation exchange capacity | cmolc/kg |

The unit is not in the observation record: it comes from the provision's row in
`provision_indicator.xlsx` (`lucas wetlab 2009`).

## Spectral observations

LUCAS 2009 soil samples were scanned on a FOSS XDS Rapid Content Analyzer. Spectral data is
stored as a diffuse-reflectance array per sample scan, generated from the source CSV's `spc.*`
columns by `lucas_2009_to_xspatula.py` — see [Prepare data]. Unlike the lab observations above,
spectral data needs one extra step first: registering the instrument's wavelength axis.

| Instrument | Provision | Provision tag |
|---|---|---|
| FOSS XDS Rapid Content Analyzer | `foss xds rapid content analyzer` (alias `foss xds rca`) | `foss-xds-rca` |

### Spectrometer

Registers the instrument's wavelength axis — the array of wavelengths every spectral
observation's reflectance array is ordered against.

**Notebook cell**: 3.5.1 Load LUCAS 2009 spectrometer (2015: 4.5.1) in `insert_lucas_data.ipynb`

**Job file**: `xspatula_lucas/lucas/import_data/LUCAS_2009/job_LUCAS_2009_spectrometer.json`

```json
{
  "process": {
    "job_folder": "import_data/LUCAS_2009/process_spectra/spectrometer",
    "process_sub_folder": "manage_process",
    "pilot_file": "xspatula_add_spectrometer_pilot.txt"
  }
}
```

**Generated by**: `step3_spectrometer()`. Process file
(`.../process_spectra/spectrometer/manage_process/foss-xds-rca_lucas 2009_spectrometer.json`):

```json
{
  "process": [
    {
      "process": "manage_spectrometer",
      "parameters": {
        "provision_id__provision_name": "foss xds rapid content analyzer",
        "wavelength_array": ["<one float per spc.* column in the source CSV>"],
        "wavelength_unit_id__wavelength_unit_name": "um",
        "provision_serial_nr_id__provision_serial_nr_name": "lucas 2009"
      }
    }
  ]
}
```

| Parameter | Description |
|---|---|
| `provision_id__provision_name` | `foss xds rapid content analyzer` — the instrument provision |
| `wavelength_array` | One value per `spc.<wavelength>` column in `LUCAS.SOIL_corr.csv`, in file column order |
| `wavelength_unit_id__wavelength_unit_name` | `um` |
| `provision_serial_nr_id__provision_serial_nr_name` | `lucas 2009` — placeholder serial number, since LUCAS 2009 used multiple physical instruments across labs |

The wavelength array's column order defines the position each value in an observation's
`@diffuse reflectance` array corresponds to — they must stay in lockstep.

**Generated by**: `step2_observation_log()`. Process file

```json
{
  "process": [
    {
      "process": "manage_observation_log",
      "parameters": {
        "sampling_log_id__sampling_log_name": "lucas_eu_2009",
        "provision_id__provision_name": "foss xds rapid content analyzer",
        "contact_name": "inherit",
        "contact_email": "inherit",
        "preparation_id__preparation_name": "ds2",
        "preservation_id__preservation_name": "ds2",
        "storage_id__storage_name": "amb",
        "laboratory": 1
      }
    }
  ]
}
```

| Parameter | Description |
|---|---|
| `sampling_log_id__sampling_log_name` | `lucas_eu_2009` — FK to the 2009 sampling log, given by its tag |
| `provision_id__provision_name` | `foss xds rapid content analyzer` |
| `name` | not given — auto named `<sampling_log_name>@<provision_name>`: `lucas european union 2009@foss xds rapid content analyzer` (tag `lucas_eu_2009@foss-xds-rca`), see [Auto naming and tags explained][auto_naming_explained] |
| `preparation_id__preparation_name` / `preservation_id__preservation_name` | `ds2` |
| `storage_id__storage_name` | `amb` (ambient) |

This `name` value is the foreign key referenced by `observation_log_id__observation_log_name` in
every spectral observation record.

### Spectra observations

One observation record per sample. Unlike the lab indicators above, the `@diffuse reflectance`
value here is an array, stored in `observation.observation_measurement_array` rather than
`observation.observation_measurement`.

**Notebook cell**: 3.5.3 Load LUCAS 2009 spectra observations (2015: 4.5.3) in `insert_lucas_data.ipynb`

**Job file**: `xspatula_lucas/lucas/import_data/LUCAS_2009/job_LUCAS_2009_observation_spectra.json`

```json
{
  "process": {
    "job_folder": "import_data/LUCAS_2009/process_spectra/observation",
    "process_sub_folder": "manage_process",
    "pilot_file": "xspatula_add_observation_pilot.txt"
  }
}
```

**Generated by**: `step7_spectra_observation()`. Process file
(`.../process_spectra/observation/manage_process/lucas european union 2009@foss xds rapid content analyzer_<POINT_ID>@0-20_a_0_none_<date>_observation.json`):

```json
{
  "process": [
    {
      "process": "manage_observation",
      "parameters": {
        "observation_log_id__observation_log_name": "lucas european union 2009@foss xds rapid content analyzer",
        "sample_id__sample_name": "<POINT_ID>@0-20",
        "provision_id__provision_name": "foss xds rapid content analyzer",
        "subsample": "a",
        "replicate": 0,
        "observed_at": "<date, ISO 8601>",
        "provision_serial_nr_id__provision_serial_nr_name": "lucas 2009",
        "@diffuse reflectance": ["<one float per spc.* column, 1/exp(absorbance)>"]
      }
    }
  ]
}
```

| Parameter | Source | Description |
|---|---|---|
| `observation_log_id__observation_log_name` | fixed | FK to the observation log above |
| `sample_id__sample_name` | `POINT_ID` | FK to the sample record (format `<point_id>@0-20`) — see [Samples explained] |
| `provision_id__provision_name` | fixed | `foss xds rapid content analyzer` |
| `subsample` / `replicate` | fixed | `a` / `0` — LUCAS 2009 ships one scan per sample |
| `observed_at` | `date` column | ISO 8601 timestamp |
| `provision_serial_nr_id__provision_serial_nr_name` | fixed | FK to the spectrometer serial record above |
| `@diffuse reflectance` | `spc.*` columns | Reflectance array, one value per wavelength in the spectrometer's `wavelength_array`, computed as `1 / exp(absorbance)` from the CSV's raw values |

The `@diffuse reflectance` array's column order must match the spectrometer's `wavelength_array`
exactly — both are built from the same `spc.*` column iteration in the source CSV, so this holds
as long as the script isn't modified to reorder one independently of the other.

## Landscape observations

Land cover (`LC1`) and land use (`LU1`) are recorded per point in `LUCAS.SOIL_corr.csv`. They
describe the geolocation, not the soil sample, so they reference `geolocation_id` rather than
`sample_id`, and use their own processes instead of `manage_observation`.

### Land cover and land use

**Notebook cells**: 3.6.2 (land cover) and 3.6.3 (land use) in `insert_lucas_data.ipynb` (2015: 4.6.2, 4.6.3)

**Job files**: `job_LUCAS_2009_land_cover.json` and `job_LUCAS_2009_land_use.json`

**Generated by**: `step8_land_cover()` and `step9_land_use()`, one file per point under
`process_landscape/land_cover/` and `process_landscape/land_use/`, e.g.
`lucas_eu_2009_38622598_land_cover.json`:

```json
{
  "process": [
    {
      "process": "manage_land_cover_observation",
      "parameters": {
        "observation_log_id__observation_log_name": "lucas european union 2009@human interpretation",
        "geolocation_id__geolocation_name": "fr_lucas@38622598",
        "landcover_id__landcover_name": "b13",
        "observed_at": "2010-06-28T11:55:49+00:00"
      }
    }
  ]
}
```

`manage_land_use_observation` is identical except for the key, `landuse_id__landuse_name`, with
the lower-cased `LU1` code (e.g. `u111`). `observed_at` is the point's actual 2009 survey date.

**The class tables.** Each classification scheme is **one table** —
`landscape_utility.landcover` and `landscape_utility.landuse` — holding all three ranks,
order > family > genus, like a taxonomy:

- each class row points to its parent class in the same table (`parent_landcover_id`,
  `parent_landuse_id`; an order has no parent);
- each class row names its rank (`class_rank_id`) in the shared catalogue
  `landscape_utility.class_rank` (`order`, `family`, `genus`);
- the LUCAS code is the class **alias**: `b` (order cropland) → `b10` (family cultivated
  cropland) → `b13` (genus).

The observation key `landcover_id__landcover_name` thus takes the LUCAS code at **whatever rank
the surveyor recorded it** — genus (`b13`), family (`e20`) or order — and resolves it by name or
alias in that one table. About half of the 2009 points are recorded at family or order rank; in
the 50-point test sample, land cover is 27 family + 23 genus and land use is 37 genus + 10 family
+ 3 order. In machine learning, the classes can be rolled up to one rank with `covariate_rank`
(see [Covariates and ranks][covariate_ranks]).

The tables are filled from `landcover.xlsx` and `landuse.xlsx` in
[Insert utility][insert_utility] (cell 1.4); the Excel layout is in
[Utility explained → Land cover and land use][utility_ranked].

## Biogeographic region (BIOGEO16) observations

BIOGEO16 assigns each point to one of the EEA biogeographic regions (`continental`,
`mediterranean`, `boreal`, ...). It comes from `LUCAS-Master-Grid.csv` (column `BIOGEO16`, joined
by `POINT_ID`), not from the LUCAS 2009 files. The region names themselves are a landscape
catalogue (`biogeo16.xlsx`) inserted in [Insert utility][insert_utility] (cell 1.4).

### Why BIOGEO16 has its own sampling log

The regions are **not observed by LUCAS**. They are a map product: the
[EEA biogeographical regions](https://www.eea.europa.eu/en/datahub/datahubitem-view/11db8d14-f167-4cd5-9205-95638dfd9618),
compiled by the European Environment Agency for the Habitats Directive and the Emerald Network,
2016 version. Attaching them to the LUCAS sampling log would claim that the LUCAS surveyors
recorded them in 2009. Instead the provenance chain says what really happened:

| Level | LUCAS soil data | BIOGEO16 |
|---|---|---|
| data source | `esdac-jrc` | `eu-eea` (European Environment Agency) |
| dataset | `lucas` | `biogeo16` |
| campaign | `lucas european union` / `lucas_eu` | `biogeo16 european union` / `biogeo16_eu` |
| sampling log | `lucas european union 2009` / `lucas_eu_2009` | `biogeo16 european union 2016` / `biogeo16_eu_2016` |
| observation log | `...2009@human interpretation` (land cover/use) | `biogeo16 european union 2016@compilation` / `biogeo16_eu_2016@compilat` |
| observed at | each point's survey date | fixed `2016-03-31`, the map's vintage |

The dataset and campaign come from `dataset.xlsx` and `campaign.xlsx` in
[Insert dataset metadata][insert_dataset_meta]. The sampling log and observation log are written
by the prepare script. Like land cover and land use, the observations reference the
**geolocation**, not the sample, so the same region value serves the 2009 and the 2015 samples at
a revisited point.

The sampling log and observation log are identical in `lucas_2009_to_xspatula.py` and
`lucas_2015_to_xspatula.py`: whichever survey round you load second finds them already in place.
